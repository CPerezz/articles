How can two reth databases differ 64× on the same benchmarks, and then agree?

Ethereum · reth · MDBX · benchmarking · 2026 · reproducible pipeline & data →

The same EEST benchmarks ran up to 64× slower on a generated reth database than on a mainnet snapshot. None of the causes were in reth. With all six fixed and three refinements on top, 153 of the 154 tests that run half a second or more agree within ±10%.

jochemnet is a mainnet shadowfork snapshot. state-actor writes synthetic state straight into reth's tables. benchmarkoor runs the same 266 EEST bloatnet tests against both, restoring the store before each one. Every ratio below is state-actor's throughput over jochemnet's, so 1.00 is parity, and a test is in band within ±10% on two independent pairs of runs. Tests under half a second are shown but not scored: they barely reproduce against themselves.

The problem: up to 64× apart

1. The test rig read the disk one request at a time

Both databases lived inside a disk image, attached through Linux's loop device. In its default mode the loop device passes reads to the disk one at a time, so reth's many parallel reads waited in line. It also read ahead, fetching data nobody asked for, which hurt state-actor's layout of contract code most.

Switching it to direct I/O fixed both: every test that reads state got 2–9× faster. Everything below is measured that way. Our earlier geth and Besu runs on this host used the same default.

2. The two stores used different storage layouts

jochemnet was a v1 store; state-actor writes v2. reth has two storage layouts: the older v1 looks accounts up by address, the current v2 by hash. EEST's sequential tests read neighbouring addresses, which v1 finds together and v2 scatters. So the two stores weren't doing the same work, and that was most of the gap.

New reth nodes use v2, so we converted jochemnet. From here on, every gap is state-actor's.

3. Rows out of order, and trie rows reth never stores

state-actor wrote accounts in the order it generated them, which is random against the table's hash order, so nearly every insert split a page in half. PR1 writes them in key order.

state-actor stored every node, so state-root updates read rows reth would never have written. PR2 stores only what reth would. Neither PR changes the state root.

4. Page fill is a dial, and mainnet's pages aren't full

Once writes arrive in key order, how full each page ends up is a choice, and it decides how many pages a lookup touches. jochemnet's account and storage tables carry years of random inserts, so their pages are well short of full.

PR3 puts the rest of state-actor's writes in key order. PR4 lets it choose how full each table's pages end up, with a migrated setting that matches a node converted to v2.

5. The wrong storage shape, and too many accounts

state-actor gave every contract a few hundred slots. Mainnet storage is heavy-tailed: most contracts hold one slot, a few hold millions.

The shape matters because reth stores no storage roots:

  • A contract with up to about 28 slots keeps them in its own row. A bigger one gets a separate sub-tree.
  • When a block changes an account, reth re-hashes its path in the account trie, which needs the storage root of every sibling on that path.
  • For a mainnet-shaped sibling that's one row reth often reads anyway. For one of state-actor's contracts it was a walk through a sub-tree.

PR5 draws each contract's size from the distribution measured on jochemnet. We also generated the store at jochemnet's account count (the original had 21% more) and matched the fill of the one big test contract. The new state needed new fixtures, which reth itself filled, and reth checked every trie node of the new store: nothing to repair. PR6 draws the largest contracts too, with no cap, so they grow with the store.

Then: accounts that look like mainnet's

state-actor's accounts didn't look like mainnet's: big balances and nonces, and almost no contracts with code but no storage. PR8 fixes that, but account reads barely get faster.

A block that reads accounts touches one row page per account it reads, however small the row, so smaller rows don't help. What still differs is the index above the rows: jochemnet's index pages are fuller, so state-actor's index has about 16% more pages.

PR7 writes each contract's trie rows in address order, so the top level of the contract-trie table now fills like jochemnet's (Figure 8, StoragesTrie).

Where it stands

Over a second, 113 and 113 of 114 tests are in band on the two pairs; each store against itself manages all 114. state-actor leans 1.4% fast there, under the 3% we set out not to chase.

What's left

  • sload, bloated contract, 240M. One test stays just outside the band, on the fast side. It reads only the big test contract, whose rows are identical in every store. In PR1-5 it was sstore, no-op write, 160M instead, now back in band. Which test sits just outside changes between regenerations.
  • Distinct code. Mainnet holds far more of it (Figure 8, Bytecodes), so code-heavy reads still run 2% fast. That's the generator's code pool, not the layout.
  • The account index. Account reads still run 2% slow, and the gap is index pages (Figure 12). The generator's fill control fills index pages like row pages; jochemnet's index pages are fuller.
  • HashedStorages' top-level tree takes 11% more pages per contract than jochemnet's at any fill setting. That density is the snapshot's years of history.
  • Short tests. Under a second, jochemnet run twice agrees with itself on only 69% of tests, so below half a second we don't score.

Four of the six causes change nothing a state root can see, and none was in reth. A comparison between a generated store and a real one should state how each was laid out, not just what it holds.
