How can two Erigon databases holding the same state be 2× slower and 3× faster, and then agree?

Ethereum · erigon · MDBX · snapshot files · benchmarking · 2026 · reproducible pipeline & data →

We ran the same EEST bloatnet benchmarks against two Erigon databases that hold the same state. On the benchmark's own clock, the one generated from scratch ran ether transfers 1.8× slower. Timed through the commit that follows each block, it was 2.8× faster. It was neither. Three things about how the two stores were built made both gaps, and a fourth made part of what was left. Fix them one at a time and the tests that run over a second land at a median of 0.96 on newPayload and 0.99 whole, 98 of 110 inside ±10%, about what one store gets against itself. Here's each one, what it did to the numbers, and what's still off.

The problem: the same state, 2× slower and 3× faster

Two databases with the same accounts: a mainnet shadowfork snapshot at block 24,402,727 (we call it jochemnet), and the same state written from scratch by state-actor. Same fixtures, same machine, same drive read with direct I/O, page cache dropped between tests. Every number here is state-actor's throughput divided by jochemnet's: 1.00 is parity, 0.50 means the generated store is twice as slow.

Each dot is one test, one colour per pair. The white tick is the category's median; the numbers on the right are that median and how many of its tests land inside ±10%. The same rows and axis come back at the end.

Over a second, the calls that load a contract's code run at parity, and ether transfers at 0.55, about half speed. The short tests point the same way, though they don't count: reads of contract accounts and plain calls sit at 0.35 to 0.47, while the controls, which touch no state, sit at 1.30. Whatever separates the two stores is in looking up accounts.

The benchmark times half of each block. Its throughput counts only engine_newPayload, where Erigon executes the block. Erigon writes the block's state in the forkchoiceUpdated call that follows. On jochemnet that call takes 4.3 to 11.9 seconds a block; on state-actor, 69 to 695 milliseconds. Add it to both sides and the picture flips.

Over a second, every row favours the generated store once the commit counts, from 2.1× on the code calls to 4.0× on the transfers. The two clocks answer different questions, so this page shows both.

Two kinds of test. A test that runs for ten seconds and one that runs for a tenth of a second aren't measuring the same thing. Every test boots a fresh client, so under a second we're timing a young process. Every view here is split at one second of newPayload time on jochemnet. Under a second, one store measured twice lands only 48% to 58% of its tests within ±10% of itself; over a second, 84% to 100% do. Timing the whole block doesn't rescue the short ones (58% to 73%). Sub-second tests are always shown and never counted as evidence.

The last clue is where each store keeps its state. Erigon has two places for it: a database (MDBX) for recent writes, and immutable files for everything older. Jochemnet's files end at block 24,349,407, and everything after that is in its database, 584 GB of it, including the 7,736 pre-run blocks that create the accounts the benchmark reads. State-actor writes all of its state into files: a 4.3 GB database beside 541 GB of files. On the tests that read contract accounts, its newPayload reads 7× the bytes jochemnet's does.

Three things made the gaps, and a fourth made part of what was left:

  1. the benchmark's state never left jochemnet's database;
  2. jochemnet carried a code cache into every boot;
  3. Erigon compresses a contract's code, and state-actor writes it raw;
  4. state-actor writes the rest of Erigon's files in their oldest format.

1. The newest 61,057 blocks never left jochemnet's database

Erigon keeps state in two places. Recent writes live in a database (MDBX). Older history is frozen into immutable files one step at a time, 1,562,500 transactions per step, and Erigon never freezes a step that isn't full. A read asks the database first and walks the files, newest first, only on a miss.

We traced it. We recorded which file every page came from while four of these tests ran. On jochemnet, at least 99% of what newPayload read came from the database, on every one. On state-actor, none did. The account read went to the account files and their indexes, and the jumpdest call mostly to the code files (79%). The transfer and the storage write went mostly to the commitment files, the trie Erigon recomputes the state root from.

Why jochemnet's state is in the database. Its files end where step 2,099 begins, at block 24,349,407. The 61,057 blocks after that hold 1,212,682 transactions. Counted the way Erigon counts, with two bookkeeping entries per block, that's 85% of one step. So all of it sits in the database, on any node. Erigon's own housekeeping can't move it: erigon snapshots retire, run on the promoted image, built no state file (124 domain files before and after).

On mainnet a step fills fast. Just before the fork, mainnet blocks carried 340 transactions each, so a step took about 4,600 blocks, some 15 hours. The shadowfork's blocks carry 17. One unfinished step stretched over all 61,057 of them, and everything written after block 24,349,407, the pre-run included, landed in it.

State-actor does the opposite. It writes all 429 million accounts straight into frozen files, as if every one of them were old.

So jochemnet measures the best case, and state-actor the worst. These benchmarks exist to find what a cold state read costs at its worst. In Erigon, that's an account whose only copy is in the oldest file: the lookup misses the database, passes every newer file and lands at the bottom. State-actor's store is built that way. Jochemnet's isn't. The pre-run creates the accounts the tests read, so they sit in the database, the first place Erigon looks. It's the same thing the pre-run did to the Nethermind and Besu snapshots: it makes the benchmark's accounts the newest data in the store.

The commit is skewed by the same cause. Jochemnet writes every block into a 584 GB database; a running node keeps only its newest step there.

So the store to fix is jochemnet. We could have gone the other way, and written the tested accounts into state-actor's database as an unfinished step. Then both stores would measure the best case: a lookup that ends in the first place Erigon looks. That isn't the read these benchmarks exist to price, and it isn't the one a node makes for cold state. On a node, everything older than the newest step is in files. So jochemnet's tested state moves down, out of the database and into the bottom file, and state-actor stays as it is.

The fix is a rebuild. Erigon won't freeze the unfinished step, so we wrote the files with Erigon's own code. A small tool reads the latest value of every key, from the database and the files alike. It writes one file per domain, covering everything up to the head block: 355 million accounts, 1.82 billion storage slots, 68 million code entries and the commitment trie. The step size becomes the head's last transaction number plus one, 3,281,022,286, so the file ends exactly at block 24,410,463. That's how state-actor's store is laid out too: one file per domain, all of it step 0. Then the database's state tables are emptied, and it shrinks from 584 GB to 7.5 GB.

Nothing moved but the shelf. Before and after, we asked the node the same 339,329 questions: balances, nonces, storage, code, and Merkle proofs that walk the state trie. 799 accounts and 335,750 slots among them had lived only in the database. Every answer came back byte for byte the same.

What it did. The rebuilt jochemnet is slower, so 110 tests now run over a second, against 55 before; every step from here on is compared on that split. Over a second, 50 of 110 tests now sit inside the band, against 18; timed whole, 28 against 0. newPayload went from 0.52 to 0.90 (0.92 in the second pair), and the whole block from 3.02 to 0.95. Account reads went from 0.35–0.47 to 0.87–0.98, and ether transfers from 0.53 to 0.93.

Two rows went the other way. The distinct-contract and jumpdest calls were at parity and now sit at 0.56 and 0.64. They had agreed for the wrong reason, and finding 3 is why.

2. Jochemnet carried a code cache into every boot

Erigon's own log splits that call in two: writing the block, and pruning. We matched each line to its test. On the untreated store, the measured block's write took 3 s at the median. That's finding 1's database. After the rebuild it takes 15 ms, and state-actor's 8 ms.

The transfers kept 3.4 seconds, 3 of them in the prune. A fresh Erigon process sizes its code cache on its first prune, by reading the whole table once. That table holds contract code Erigon has already decompressed, so a hit skips the code files. Jochemnet's held 143,219 contracts' code. The rebuild left it alone, because it isn't state. State-actor's is empty. Every test boots a fresh client, so jochemnet pays the read once per test. Most tests send a setup block first, and that block pays it. A transfer test sends one block, so the measured one does.

The fix is to empty the table. On a miss Erigon reads the code files, which is what state-actor does on every call, so an empty cache is the worst case again. What it did: the first prune went from 3 s to under 3 ms on every test. The transfers' call dropped from 3.43 s to 904 ms, against state-actor's 651 ms, and their whole block from 1.90 to 1.03. Timed whole, 63 of 110 tests over a second now sit inside the band, against 28.

Inside newPayload, one row over a second moved by more than 0.05 in both pairs: the distinct-contract call, from 0.56 to 0.64 (0.65 in the second pair). Jochemnet ran it 9% slower, and state-actor 2%. So the cache had been serving some of those contracts' code: the pre-run deployed them, and Erigon caches code as it deploys it. The jumpdest call didn't move; its code came from the files all along, as the trace showed.

3. Erigon compresses a contract's code; state-actor writes it raw

After the first two fixes, two rows were still slow: calls into a different maximum-size contract every time, at 0.64 for a distinct contract and 0.63 for the jumpdest one. Calls into a reused contract of the same size ran at 0.96.

Only distinct contracts reach the disk. Erigon looks up code by its hash first, in memory and then in the cache table from finding 2, and reads the code file only on a miss. A reused contract has one hash, so each fresh client reads it from disk once. A distinct contract is a new hash every call, and every call reads the file.

The contracts are the same; the files aren't. Every test contract is 24,576 bytes, almost all of it one repeated opcode; the distinct ones carry their own address inside. All 335,000 that jochemnet holds are on state-actor too, byte for byte. Erigon's writer compresses code against a dictionary of repeated byte patterns: jochemnet's code file carries 676 KB of them, and a test contract takes 197–203 bytes, one page for its key and value (1.06 on average). State-actor writes Erigon's file format with its own encoder, which has no dictionary path. Its dictionary is empty, and every test contract takes all 24,577 bytes, seven pages, on every call.

Why the rows agreed before. Before the rebuild, jochemnet's test contracts sat in its database, which keeps values as written: all 24 KB of each, like state-actor's file. Both stores paid for whole contracts, and the rows sat at 0.99 and 1.06. Finding 1's rebuild wrote them the way Erigon writes every file, and the gap showed.

The test is to write state-actor's code file the way Erigon does. We re-encoded it with Erigon's own compressor and the code domain's own settings. Every key and value stays: the file's 16,686,745 entries hash the same before and after, and 4,837 eth_getCode answers, 1,500 of them test contracts, came back byte for byte the same. The file went from 49.6 GB to 16.7 GB.

What it did. The distinct-contract call went from 0.64 to 0.98 (0.96 in the second pair), and the jumpdest call from 0.63 to 0.96 (0.96). Two other rows moved: account reads on the same two kinds of contract, one up and one down. They don't read code, and one store measured twice keeps only 2–3 of their 4 tests within 10% of itself. Over a second, 93 of 110 tests now sit inside the band, against 63.

The fix belongs in the generator: its Erigon writer has to hand each domain to Erigon's own compressor, at Erigon's own settings.

4. State-actor writes Erigon's oldest file format

The code file wasn't the only one. Erigon names each file after its format version. State-actor writes every other state file at v1.0, the oldest one Erigon still reads. Erigon writes v2.0 to v2.2, with newer indexes and filters beside them. It also compresses the keys of the storage and commitment files (storage, commitment), which state-actor writes raw.

The test is the same as for the code file: re-encode the other three with Erigon's own writer, at its current versions. Every key and value stays: 947 million commitment entries, 2.21 billion storage slots and 431 million accounts hash the same before and after, and 4,367 answers to eth_getStorageAt, eth_getBalance and eth_getProof came back byte for byte the same. The storage file went from 181 GB to 165, the commitment file from 282 to 278, and the account file kept its size.

What it did. Over a second, 98 and 97 of 110 tests now sit inside the band, against 93 and 88. Of the five the first pair gained, three are account reads, and three of those four rows now sit inside in both pairs. But the medians moved apart: 0.971 to 0.964 in the first pair, 0.960 to 0.974 in the second. Timed from where Erigon starts on the block (below), state-actor's execution went from 6.2% behind to 4.5%.

Why it didn't close. State-actor reads what it read before. On the account read, what it reads beyond jochemnet is the account index, and an index grows with the keys it holds. State-actor's account index is 1.03 GB against 0.85, for 431 million accounts against 355 million. So the format was about a quarter of the lean in execution. The account count is what's left that we know of, and it takes a store generated at jochemnet's size to test.

The fix belongs in the generator as well: Erigon's current file versions, beside its compressor.

Which families are still off. Not every test sits inside the band, and one store measured twice doesn't manage that either. So the next figure puts each row's median beside the medians each store gets against itself.

Under a second, blocks with no state work run faster on state-actor. Controls, warm queries and reloads of one slot sit at 1.12–1.55 in both pairs, while each store measured twice centres them on 0.93–1.01. So it isn't noise. At the median, jochemnet spends about 16 ms more per block. That's 36% of their median block (44 ms on state-actor), and about 1% of a block over a second. It was there untreated, at 1.20–1.30.

The 16 ms is a lookup, not state. Erigon logs Handling new payload when it starts on a block. On those blocks, jochemnet logs it 16 ms after the request arrives and state-actor after 2 ms. From there the block takes about the same on both: 44 and 41 ms. Before that line, Erigon checks whether it already knows the block's hash. A new block isn't in its database, so the check walks the frozen header files, newest first. Jochemnet carries 65 of them, mainnet's history. State-actor starts at genesis and has none.

It's the page cache. benchmarkoor drops it before every test, so each of those checks reads from disk. Asking each store for a block hash it doesn't have shows the cost. Cold, jochemnet takes 18.7 ms and reads 637 KB: index pages from 63 of its 65 header files, plus its database. Warm, it takes 1.1 ms and reads nothing. State-actor takes 1.2 ms either way and reads nothing. Traced page by page on six of these tests, jochemnet reads 500–709 KB before the line, all of it block files and its database. State-actor reads nothing.

So it's chain history, not state. A running node keeps those pages in memory; only a benchmark that empties the cache pays for them on every block. Timed from the line on, the three rows land at 0.93–1.06 (up to 1.14 in the second pair), and 73 of 156 tests under a second sit inside the band instead of 26.

Over a second, the lean is in execution. The pairs sit at 0.964 and 0.974, where each store measured twice centres on 0.99. Most tests that miss the band miss it low: 10 of 12, and 10 of 13 in the second pair. The same check costs jochemnet 17 ms there, and both stores spend over 200 ms before it on work they share. Leave both out and state-actor executes 4.5% slower, in both pairs (ratios of 0.956 and 0.954). Finding 4 took it down from 6.2%; what's left lines up with the extra accounts.

What's left, and why

  • State-actor's Erigon writer doesn't write Erigon's files yet. It needs Erigon's compressor and Erigon's current file versions. Until it has both, every Erigon store it builds needs re-encodes like the ones above: 6 hours for the code file and 6 for the other three.
  • The 4.5% lean in execution over a second. It follows the account count, which only a store generated at jochemnet's size can test.
  • The test contracts are cheaper than real ones. Each is 24 KB of one repeated opcode, so Erigon stores it in about 200 bytes, one page. Jochemnet also holds 1,595 real mainnet contracts of the same size, and the median one takes 24,578 bytes, seven pages. So the distinct-code rows price a cheap code read, not the worst one. That's a question for the fixtures, not the stores.
  • Distinct code is still open on the other clients. On Nethermind and Besu the same rows end with the generated store faster, not slower. There state-actor writes code through the client's own RocksDB settings, so the encoding matches; what differs is the code packed around each test contract. State-actor's shared code pool keeps every record at 1 KiB or more, and the Nethermind article traces the overshoot to that floor. The pool feeds every client, so changing it changes every generated store's state root.
  • Both stores keep each domain in one file. On a node, files come in merged ranges, and a cold lookup checks each newer file before it reaches the oldest. Neither store here pays that walk. It's the same on both sides, so the ratio holds, but a node's worst case costs more than either store measures.
  • Sub-second tests can't be compared on this harness yet. Every test boots a fresh client, and under a second the measurement is mostly that client starting up. Dropping the page cache before each test also makes jochemnet pay for its chain history on every block. A discarded burn-in block before the measured one would fix both. Until then, those numbers are shown and not counted.
  • benchmarkoor's clock still stops at newPayload. With all four steps the two clocks agree, so this comparison doesn't depend on it. But on the untreated store the commit was most of each block, and a newPayload-only number hid it. For Erigon, the harness should report the whole block beside newPayload.

None of these is a reason to distrust the generated store on tests over a second, once its files are written the way Erigon writes them. Two are generator work, one is still open, one is a question for the fixtures, and three are about the method and the harness.
