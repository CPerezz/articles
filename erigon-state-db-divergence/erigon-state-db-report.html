How can two Erigon databases holding the same state differ 5×?

Ethereum · erigon · MDBX · snapshot files · benchmarking · 2026 · reproducible pipeline & data →

We ran the same EEST bloatnet benchmarks against two Erigon databases that hold the same state. On every test over a second that reads an existing account, the one generated from scratch came out slower, up to 5× on contract calls. That's what the benchmark reports, and it times only half of each block. Erigon writes a block's state in the call that follows it, and there the gap runs the other way. Here's the baseline, and where it points.

The problem: the same state, up to 5× apart

Two databases with the same accounts: a mainnet shadowfork snapshot at block 24,402,727 (we call it jochemnet), and the same state written from scratch by state-actor. Same fixtures, same machine, same drive, page cache dropped between tests. Every number here is state-actor's throughput divided by jochemnet's: 1.00 is parity, 0.20 means the generated store is five times slower.

Each dot is one test, one colour per pair. The white tick is the category's median, and the numbers on the right are that median and how many of the category's tests land inside ±10%. The same rows and the same axis come back in the next figure.

The tests that read existing accounts are 3 to 5 times slower on the generated store. The controls run the same loop and touch no state, and they sit at 1.30: faster on the generated store, not slower. Calls that touch an account that isn't there sit at 1.00. Whatever this is, it's about reading state that exists.

The benchmark times half of each block. Its throughput counts only engine_newPayload, where Erigon executes the block. Erigon writes the block's state to disk in the forkchoiceUpdated call that follows. On jochemnet that call takes 3.4 to 11.8 seconds per block. On state-actor it takes 15 to 638 milliseconds. Add it to both sides and the picture changes.

Over a second, the rows now spread from 0.38 to 3.42. Calls and account reads stay slower on the generated store: what it loses executing is more than jochemnet loses committing. Storage writes, calls to absent accounts and ether transfers go the other way. The two numbers answer different questions, so this page shows both.

Two kinds of test. A test that runs for ten seconds and one that runs for a tenth of a second aren't measuring the same thing. Every test boots a fresh client, so under a second we're timing a young process. Every view here is split at one second of newPayload time on jochemnet. Under a second, one store measured twice lands only 49% to 52% of its tests within ±10% of itself; over a second, 98% to 100% do. Timing the whole block doesn't rescue the short ones (54% to 64%). Sub-second tests are always shown and never counted as evidence.

The last clue is where each store keeps its state. Erigon has two places for it: a database (MDBX) for recent writes, and immutable files for everything older. Jochemnet's files end at block 24,349,407. Everything after that is in its database, 584 GB of it. That includes the 7,736 pre-run blocks that create the accounts the benchmark reads. State-actor writes all of its state into files at genesis: a 4.3 GB database beside 541 GB of files. On the account-row tests, its newPayload reads 7× the bytes jochemnet's does (2.48 GB against 0.34 GB).

Same state, different shelves. That points at two things to test: reads from files against reads from the database, and a database big enough to slow every commit.

1. The newest 61,056 blocks never left jochemnet's database

Erigon keeps state in two places. Recent writes live in a database (MDBX). A background job freezes each finished step of history into immutable files, then clears it from the database. A read asks the database first and walks the files, newest first, only on a miss.

The benchmark switches that job off. Its erigon config passes --exec.no-background-maintenance, which stops the client building any file, and --exec.no-prune, which stops it clearing the database. The flag's own help calls it “NOT an operational setting”. Jochemnet's files end at block 24,349,407. Everything after that is in its 584 GB database: 53,320 blocks of the shadowfork, and the 7,736 pre-run blocks that create the accounts the tests read.

State-actor does the opposite. It writes all 429 million accounts straight into frozen files, as if every one of them were old. Its database holds the chain's configuration and little else, 4.3 GB against 541 GB of files. So a lookup that the snapshot answers from its database has to miss there on the generated store and go to the files. That's our explanation for the extra bytes in the figure, and the fix below tests it. The one row where both read the same is the absent account (0.37 GB against 0.36 GB): a key that exists nowhere can't be answered from the database on either store. It would also explain why the commit runs the other way: one store writes every block into a 584 GB database, the other into an empty one.

Which one is right? Neither is exactly how a node runs. A node in normal operation freezes every finished step and clears it from its database. So an account created long ago, which is what these tests mean by an existing cold account, is read from a file. State-actor gets that right. Its database lacks only the newest, unfinished step, which Erigon never freezes. Jochemnet keeps 61,056 blocks there, all but the newest step of which a running node would have frozen.

The fix is Erigon's own housekeeping, run once on the promoted jochemnet image with the client stopped. erigon snapshots retire builds the missing files, merges them and clears the database. Then mdbx_copy -c compacts it. No value changes, so the head's state root stays the same; only where each value lives does. The benchmark's flags stay on for the tests, so housekeeping still can't run while a test is timed.

We change the snapshot and not the generated store for two reasons. The generated store is the closer of the two to a running node here. And Erigon does this itself, while moving state-actor's accounts into the database would take a change to the generator.

What it should do. If this is the gap, jochemnet's newPayload slows on the account and call tests, its commit drops under a second, and the ratio over a second moves from 0.31 toward 1.
