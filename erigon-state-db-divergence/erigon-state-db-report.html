How can two Erigon databases holding the same state be 2× slower and 3× faster?

Ethereum · erigon · MDBX · snapshot files · benchmarking · 2026 · reproducible pipeline & data →

We ran the same EEST bloatnet benchmarks against two Erigon databases that hold the same state. On the benchmark's own clock, the one generated from scratch ran ether transfers 1.8× slower and contract calls at parity. But that clock stops at newPayload. Erigon writes each block's state in the call that follows, and there the snapshot spends 4 to 12 seconds a block. Timed whole, the generated store is 2.8× faster. Here's the baseline, and where it points.

The problem: the same state, 2× slower and 3× faster

Two databases with the same accounts: a mainnet shadowfork snapshot at block 24,402,727 (we call it jochemnet), and the same state written from scratch by state-actor. Same fixtures, same machine, same drive read with direct I/O, page cache dropped between tests. Every number here is state-actor's throughput divided by jochemnet's: 1.00 is parity, 0.50 means the generated store is twice as slow.

Each dot is one test, one colour per pair. The white tick is the category's median, and the numbers on the right are that median and how many of the category's tests land inside ±10%. The same rows and the same axis come back in the next figure.

Over a second, the calls that load a contract's code run at parity. Ether transfers run at 0.55, close to half speed. The short tests point the same way, though they don't count. Reads of contract accounts and plain calls sit at 0.35 to 0.47; the controls, which touch no state, sit at 1.30. Whatever separates the two stores is in looking up accounts, not in running code.

The benchmark times half of each block. Its throughput counts only engine_newPayload, where Erigon executes the block. Erigon writes the block's state to disk in the forkchoiceUpdated call that follows. On jochemnet that call takes 4.3 to 11.9 seconds per block. On state-actor it takes 69 to 695 milliseconds. Add it to both sides and the picture changes.

Over a second, every row favours the generated store once the commit counts: from 2.1× on the code calls to 4.0× on the transfers. The two numbers answer different questions, so this page shows both.

Two kinds of test. A test that runs for ten seconds and one that runs for a tenth of a second aren't measuring the same thing. Every test boots a fresh client, so under a second we're timing a young process. Every view here is split at one second of newPayload time on jochemnet. Under a second, one store measured twice lands only 48% to 58% of its tests within ±10% of itself; over a second, 84% to 100% do. Timing the whole block doesn't rescue the short ones (58% to 73%). Sub-second tests are always shown and never counted as evidence.

The last clue is where each store keeps its state. Erigon has two places for it: a database (MDBX) for recent writes, and immutable files for everything older. Jochemnet's files end at block 24,349,407. Everything after that is in its database, 584 GB of it. That includes the 7,736 pre-run blocks that create the accounts the benchmark reads. State-actor writes all of its state into files at genesis: a 4.3 GB database beside 541 GB of files. On the tests that read contract accounts, its newPayload reads 7× the bytes jochemnet's does.

Same state, different shelves. That points at two things to test: reads from files against reads from the database, and a database big enough to slow every commit.

1. The newest 61,057 blocks never left jochemnet's database

Erigon keeps state in two places. Recent writes live in a database (MDBX). Older history is frozen into immutable files one step at a time, 1,562,500 transactions per step, and Erigon never freezes a step that isn't full. A read asks the database first and walks the files, newest first, only on a miss.

We traced it. We recorded which file every page came from while four of these tests ran. On jochemnet, at least 99% of what newPayload read came from the database, on every one. On state-actor, none did. The account read went to the account files and their indexes, and the jumpdest call mostly to the code files (79%). The transfer and the storage write went mostly to the commitment files, the trie Erigon recomputes the state root from.

Why jochemnet's state is in the database. Its files end where step 2,099 begins, at block 24,349,407. The 61,057 blocks after that hold 1,212,682 transactions. Counted the way Erigon counts, with two bookkeeping entries per block, that's 85% of one step. So all of it sits in the database, on any node. Erigon's own housekeeping can't move it: erigon snapshots retire, run on the promoted image, built no state file (124 domain files before and after).

On mainnet a step fills fast. Just before the fork, mainnet blocks carried 340 transactions each, so a step took about 4,600 blocks, some 15 hours. The shadowfork's blocks carry 17. One unfinished step stretched over all 61,057 of them, and everything written after block 24,349,407, the pre-run included, landed in it.

State-actor does the opposite. It writes all 429 million accounts straight into frozen files, as if every one of them were old, and its database holds 4.3 GB against 541 GB of files.

So jochemnet measures the best case, and state-actor the worst. These benchmarks exist to find what a cold state read costs at its worst. In Erigon, that's an account whose only copy is in the oldest file: the lookup misses the database, passes every newer file and lands at the bottom. State-actor's store is built that way. Jochemnet's isn't. The pre-run creates the accounts the tests read, so they sit in the database, the first place Erigon looks. It's the same thing the pre-run did to the Nethermind and Besu snapshots: it makes the benchmark's accounts the newest data in the store.

The commit is skewed by the same cause. Jochemnet writes every block into a 584 GB database; a running node keeps only its newest step there.

So the store to fix is jochemnet. Its tested state has to move to the bottom of the files, and out of the database. Erigon's own housekeeping can't do it, as the retire run showed, so it takes a rewrite of the files. That's this study's next step.
