How can two Nethermind databases holding the same state differ 17× — and then agree?

Ethereum · nethermind · flat DB · benchmarking · 2026 · reproducible pipeline & data →

1,461 tests matched by exact identity across both stores, zero gas mismatches. Nethermind nethermind:glamsterdam-devnet-7, --FlatDb.Enabled=true, rollback_strategy: container-recreate, drop_memory_caches: steps.

The behaviour

Two Nethermind databases holding the same logical state: a mainnet shadowfork snapshot at block 24,402,727, and state generated from scratch by state-actor. The same EEST bloatnet fixtures run against both on the same machine, page cache dropped between tests. Where the tests read accounts, the generated store reports up to 17× less throughput. That is not a small-test artifact: the two categories carrying it run for a median of 10.2 and 9.4 seconds.

How to read a number on this page

This suite contains two populations, and only one of them can support a claim about a database. Measure the same store twice under the same configuration: over five seconds, 97% of tests land within ±10% of themselves; under a fifth of a second, 39% do. A short test does not reproduce against itself, so a ±10% difference between two stores on a short test is not evidence.

Every test is therefore split at one second, and the two classes are reported separately. Membership is fixed once from the reference arm and used throughout.

What we found wrong with the measurement

Four findings, in the order they matter. Each was established by changing one thing and re-measuring. The first moved the headline; the second and third were plausible causes eliminated by intervention; the fourth is the residual, and it closes. The one cell that ran the other way, ether transfers, turned out to be this study's own tooling having repacked a column of the snapshot; it is traced at the end of Finding 4 and listed with the errata.

  1. The pre-run is promoted into the baseline. One arm replays a pre-run and the harness promotes the result into the image every test restores from, leaving the benchmark's own accounts as the newest versions in the youngest files of the LSM tree. Fixed; accounts for almost all of the gap.
  2. The client is restarted per test, and the two arms warm up differently. jochemnet's setup step is heavy EVM work, so its interpreter is promoted before the measurement; state-actor's spends that window on an empty block. Fixed by intervention: equalising it moves the control tests from 0.73 to 1.14.
  3. The generated store makes every client that opens it rewrite the store. A client sitting idle read 1,962 MB from it in 60 seconds against jochemnet's 0, restarted on every one of 1,463 tests. Fixed in the generator; changed the throughput by almost nothing.
  4. The harness has no compaction control and no warm-up control. BENCHMARKOOR_COMPACT_BETWEEN_STEPS is named in a source comment, never implemented, BENCHMARKOOR_POST_PRERUN_CMD is implemented on branch state-db-journal-drain only; absent from the binary these runs used, and there is no way to request a discarded burn-in block. Both treatments were applied by hand.

The root cause: the benchmark's keys live in a corner of one store

Only the jochemnet arm runs a pre-run: 7,736 blocks that create the accounts the benchmark reads, followed by promote_post_pre_runs: true, which freezes the resulting layout into the image every test is restored from. The page cache is dropped between tests, so this is not a caching effect. What survives is which files hold the current copy of each key.

Nethermind keeps flat state in RocksDB, keyed by keccak256(address). The keys are uniformly scattered, but the pre-run rewrote every benchmark account, so their newest copies sit together in a few recently flushed SSTs at the top of the LSM tree. A levelled store answers a point lookup from the newest level holding the key, so the working set is bounded by the size of those files, not by the number of keys.

The prediction follows directly: merge those files into the bottom level and the advantage must vanish, because no level then holds a privileged copy. That is a compaction, and the rest of this page is the test.

The per-lookup cost is the same. The number of distinct blocks is not: one store runs out of new blocks to read.

Finding 1: the pre-run is promoted into the baseline — and what compacting it does

The treatment is a full RocksDB compaction of the affected column families, CompactRange with bottommost_level_compaction=kForce, using the other store's exact per-family options, verified knob by knob. No value changes and the state root is unchanged; only which file holds each key's newest copy. The pre-run is then removed from the arm's config: its writes are already in the promoted image, so replaying it would rebuild the very layout just flattened.

The reproducible path is the harness's post-pre-run hook (BENCHMARKOOR_POST_PRERUN_CMD), which is on a branch and not in the binary these runs used. The compaction here was applied to the promoted image by hand; same end state.

Finding 2: the client is restarted for every test, and the two arms warm up differently

Every test boots a fresh client, 1,463 times. That keeps tests independent, and it means every measured step runs in a process seconds old. A .NET process seconds old is still compiling itself: hot methods start on the unoptimised tier and are promoted in the background after a call-count threshold. Whether the EVM's inner loop has been promoted when the measured block arrives depends on what the process did just before, and the two arms' fixtures make it do different things.

The test: remove the JIT from the measurement

If warm-up is the cause, removing it should remove the gap. DOTNET_TieredCompilation=0 compiles every method fully optimised on first call: no unoptimised tier, no background promotion, both arms on steady-state code from the first block. A second lever, disabling optimistic parallel execution, tests the alternative that state-actor's fixtures cause more transaction conflicts. Both applied to both arms, same 40 control tests.

What this is and is not. DOTNET_TieredCompilation=0 is the diagnostic, not the fix; a live node runs promoted, profile-guided code. What the benchmark needs is what a live node has: an EVM past the tiering threshold before the measured block, i.e. the same burn-in on every arm, discarded. Any JIT-hosted client restarted per test is exposed. Ahead-of-time compiled clients are not, which is why the geth study could find this cell open but not close it.

Finding 3: the generated store makes the client rewrite it

Boot each arm, drop the page cache, issue no queries, and read the client's own /proc/<pid>/io for 60 seconds. jochemnet reads 0 MB. The generated store's client reads 1,962 MB, about 33 MB/s, indefinitely, every thread at 0% CPU.

Per-thread attribution puts the traffic on rocksdb:low: RocksDB's own background compaction, not client code. The event log names the reason: 14 jobs at boot, all on StateNodes, all BottommostFiles. jochemnet's client starts 1, for the ordinary reason.

kBottommostFiles rewrites bottom-level files purely to zero their sequence numbers: every bottommost file with largest_seqno != 0 is marked once no snapshot protects it. The trigger is not the shape of the levels but how the files got there. The generator does finish by compacting, but with the default bottommost_level_compaction = kIfHaveCompactionFilter and no filter configured, so RocksDB moved the flushed L0 files into the empty bottom level rather than rewriting them. The tree comes out flat and every file keeps a non-zero sequence number.

The fix. Run the finishing compaction with bottommost_level_compaction=kForce, once, in the generator. Applied to the trie families here, 331 GB in 42 minutes, it takes the idle client from 1,962 MB to 0 MB and the boot from 14 compaction jobs to 0. Upstream as state-actor#139, which repairs the same call in the Besu, ethrex and reth writers.

What it did change is what can be measured. On a per-test byte column that is a couple of per cent; on the difference between two windows, which is what a distinct contract costs, it was most of the answer. With the store quiet, the attribution below is about the test.

Class 2 in detail: which state access actually diverges

The 785 tests over a second sit at 0.978 with 83% inside ±10%. What is left is not a general slowness; two questions locate it. Does the opcode fetch the callee's code, or only read the account row? And is the contract different on every access, or reused?

One square of a 2×2. Not the account row, since the account-row opcodes are at parity under the same mode; not distinctness on its own, since the same opcodes reusing one contract are at parity too. Only loading a distinct contract's code is expensive.

Finding 4: what is left is the reading of bytecode, and it is the generator's filler code packed around it

The residual is confined to one operation: fetching the bytecode of a contract the store has not fetched before. The opcode grid draws the line exactly. BALANCE (0.969) and EXTCODEHASH (0.972) read only the account row, and sit at parity under every access mode. Every opcode that must load the code diverges, and EXTCODESIZE is the worst of them at 0.626: it is not answered from the account row or from a cache, Nethermind fetches the bytecode to measure it.

Measured on the settled store over 6 matched pairs per arm, the generated store reads 2,821 MB to do what the snapshot does in 1,671 MB: 1.69× the bytes, 2,444 MB of it in the code column family. The account rows are identical between the two patterns (-1.0 MB) and the trie families contribute nothing (-0.1 MB). On patterns that touch no code at all, the two stores are byte-for-byte alike: 19.3 MB against 16.2 MB.

Why the obvious explanation fails

The generated store's code database is 45 GB against 7.6 GB, so the natural reading is that code lookups are simply more expensive on it. Measured in isolation, they are cheaper:

Per lookup, the generated store is the cheaper one at every granularity we can measure. The cost is therefore not in the lookup. It is in what a lookup drags in with it.

The mechanism: block tenancy

Both stores key code by its hash, so a contract's neighbours in a data block are random, and what differs is who they are. The snapshot's code database holds 19% of accounts with code at a median of 45 bytes and a wide spread; the generated store holds 31% with code, almost all of it a distinct 23-byte stub that does not compress. Tracing the client's pread calls through one EXTCODESIZE DIFF_MAX 160M test shows what that does to a fetch:

Same test, same window. The account row is byte-identical. Every code fetch is one block, and every block is 562 bytes larger on the generated store: the stubs packed around the contract. A larger compressed block crosses a 4 KB page boundary more often, so a quarter of the fetches need a second physical read, which is the 149 µs. Over 49,720 fetches that is the second by which this test runs slower (13.24–13.48 s against 14.10–14.49 s, five runs each).

Confirmed by intervention. The generated code database was rewritten with a 64-byte data block, so every contract sits in a block of its own (134,442,675 blocks for 134,442,676 entries), and the image promoted. Every key and value is byte-identical, the state root is unchanged, the fixtures are the same. The same test then ran in 13.18, 13.12, 13.26 s, on the snapshot's side of its own five runs. The same effect has been seen from the other side. state-actor#138 changed the autofill pool's content to tiled bytecode that over-compresses, and the Besu benchmark's distinct-code categories went from 17% slower than mainnet to 46–51% faster; the same cell on the Besu study's store reads 0.831 against 0.944 reused. The 64-byte block is a diagnostic, not a configuration; the fix is the pool's content, and state-actor#141 slices it from real mainnet bytecode at ±5% of mainnet compressibility. A store built that way has a different genesis state root, so the stateful fixtures must be regenerated with it; that is the remaining step.

The other direction: ether transfers

The one cell where the generated store was reproducibly faster (1.076 on the settled runs) was traced the same way, 211 against 208 seconds for 18 blocks of transfers. Account-row and code reads are identical (458,601 against 458,442; 101,589 against 101,217). The snapshot reads 630,531 top-of-trie node blocks against the generated store's 413,964. An earlier version of this page called that a property of the arms — a migrated mainnet trie costing more to update than a generated one. It is not. A flat store does not skip the trie on a write: a transfer changes two accounts and the state root needs every branch node on both paths re-hashed, so the question is why one trie needs more node reads than the other for the same work.

The tries are the same shape. Nethermind keeps the top of the account trie (paths of up to five nibbles) in its own column, keyed by path, and the rest in a second one. A full scan of the first and a sample of whole level-6 subtrees from the second, on both stores:

Whose layout was it? Not the snapshot's. Two smaller store defects turned up on the way and moved no ratio: the generated store's account family was left L3:92 (23.7 GB), compaction-pending and both arms' code databases compaction-pending, because a plain CompactRange writes into the deepest level that already holds files unless given a target level. Same family of mistake as Finding 3, on smaller column families.

The code-pool fix works, and it overshoots. Distinct-contract code execution, the cell this page spent four findings on, was 0.938 on the old store; on the regenerated one it is 1.051 and 1.093, and jump-destination scanning 1.103 and 1.075 against 0.943 before. A pool sampled from mainnet bytecode at mainnet compressibility still does not reproduce mainnet's block tenancy on this client: the pool's 1 KiB floor keeps small records out, and on a 4,096-byte code block a fixture contract then starts a block of its own more often than it does on mainnet, where the median contract is 45 bytes. Cheaper than mainnet is as wrong as dearer, and the mechanism is the same one Finding 4 measured.

Ether transfers: the layout was about half of it. With both stores packing their top-of-trie column the way the client does, transfers read 1.061 and 1.057 against 1.076 before — the snapshot gained +4.2% from the repack alone, which is the swap's per-arm figure (1.034) reproduced on a different day against a different store. What is left is small and, as the next section shows, is not a difference in reads at all.

Which tests are still outside ±10%, and why

Of the 142 tests over a second, 27 leave ±10% in the first run of the regenerated store and 23 in the second. Both runs divide by the same jochemnet run, so a single slow jochemnet measurement makes a test look reproducibly divergent in both. It does: re-running 20 of those tests as a fresh pair, back to back on the same day, moves jochemnet by up to 29% on one test (sstore slots=False new=True 240M) against 14% for state-actor. The transfers that survive the fresh denominator are not I/O. On the largest of them the two arms issue the same reads for the same bytes at the same latency: 20,211 against 20,200 account-row reads (82 MB each side, 20.1 against 20.3 ms mean), 25,316 against 25,539 top-of-trie reads, and 25,317 against 24,874 deeper ones. The clearest case is the absent-account transfer: 918 against 920 account reads, identical bytes and latency, and 144 against 99 MGas/s. Open.

The storage outlier is I/O, and it is the same mechanism as the root cause. Writing to a slot that does not exist runs 2.03–2.14× on the generated store in every run, and the reason is in the column's shape rather than its contents: jochemnet's storage column is spread over L0/L2/L3/L4/L5/L6 (807 files, 89 GB), the generated store's sits in a single L4 (331 files, 157 GB). A lookup for a key that is absent has to be refused by every level that could hold it, so the snapshot pays 3,770 storage reads against 900 for the same test. Placement again, one column over: the pre-run left the storage column as a stack of levels, and nothing in this study ever compacted it.

Where it stands

The generated state was never 17× slower. With placement equalised, the store no longer compacting itself under the measurement, and both arms on steady-state code, the tests that can support a claim agree to within a few per cent. The one operation that remained slower, fetching a contract the store has never served, was the generator's filler bytecode packed around the fixture contracts: repacked as a diagnostic that cell reads 1.008, and on a store regenerated with the pool fixed at the source it reads 1.051 — past parity, the same mechanism with the sign reversed. Of the cell that ran the other way, ether transfers, about half was this study's own tooling having repacked one column of the snapshot; with that undone the cell reads 1.061, and on a same-session pair the tests behind it issue the same reads for the same bytes at the same latency, so what is left there is not I/O at all. Four defects in the pipeline, one in the study, five interventions; what remains is a generated store that is a few per cent cheaper than a mainnet-shaped one on the two operations that touch bytecode and a few per cent cheaper on storage and transfers, in the direction that flatters the synthetic state rather than the one this page opened with.

What we got wrong on the way

  • The first compaction used RocksDB's default table options, which silently dropped the ribbon filter and switched to Snappy. Absent-account lookups inverted to a 19× advantage for the generated store, and it took a full re-run with the real per-family options to get the parity figure above.
  • A rebuild was applied to the mounted volume without promoting it, so the harness restored the untreated image before the first test and a 2.2-hour run measured nothing new. It became an accidental replication, which is the only reason we can quote a run-to-run noise figure.
  • The probe measured both stores as if they had no filters. It opened every column family with RocksDB's default options, and a reader with no filter_policy configured never consults the filters that are in the files. Absent and present lookups therefore cost the same, which made us retract a correct explanation. Opened properly, the filters work on both arms — 19,821 and 19,786 of 20,000 negatives rejected — and an absent lookup costs 73 against 7,314 bytes.
  • We published a mechanism for the last cell and it was wrong. The residual was attributed to the generated store's larger code database. Three direct measurements say the opposite: reading code is cheaper on that store per lookup, cheaper on a sweep of distinct maximum-size contracts, and the two stores hold the same number of them. The section above now reports the cell with the mechanism that survived and the intervention that confirmed it.
  • We had a fourth explanation and it failed too. The control gap looked like cross-step cache carry-over, and we pre-registered the prediction that starving the block cache would pull it to 0.85–0.95. It moved to 0.707. The section above reports the eliminated explanation rather than the one we expected to be writing, which is the only reason this list is worth keeping.
  • We reported per-test divergence counts before measuring whether a test reproduces. Running the same store twice under the same configuration puts only 75% of 133 tests inside ±10% of themselves — 39% for tests under a fifth of a second against 97% for tests over five seconds. An earlier version of this page ranked the twelve most divergent tests in the suite; all twelve ran in under 0.2 s, so that table was a ranking of the noisiest measurements. It is gone, and the dispersion figure now states the floor.
  • We blamed the wrong subsystem three times for the same gap. First the client's block cache, refuted by starving it. Then a background compaction the generated store really was running, refuted by settling the account family and watching the throughput not move. Then a much larger one on the trie families — 1,962 MB per 60 idle seconds, Finding 3 above — where the prediction on record was that most of the remaining gap would close, and it moved +0.007. The one that did explain the bulk of it was the JIT, visible only by looking at the client's threads rather than its I/O. Three of the four were eliminated by intervention rather than argument, which is the only reason the fourth was reachable.
  • We attributed bytes to the test while the store was reading on its own account. The generated store's client was compacting in the background throughout every run, and the per-column-family probes compare two separate runs — one filtered to DIFF_MAX, one to SAME_MAX, each with its own boot — so that traffic enters each window in proportion to how long the window stayed open rather than to what the test did. It landed on the difference between two large numbers, which is exactly the quantity we were reading. The effect on the per-test byte columns elsewhere in this page is small by comparison: at the measured idle rate of 33 MB/s and a DIFF_MAX test length of 1.8 s, about 58 MB against read volumes in the thousands. Re-measured on the settled store, the marginal cost of a distinct contract is 1.69× rather than the 3.15× the same probe reported while the compaction was running, and the 689 MB of trie reads we had attributed to non-code account lookups turned out to be 0. An I/O measurement taken while the store is doing its own I/O measures the store, not the test.
  • We attributed the transfer asymmetry to the arms; it was ours. The snapshot read 47% more top-of-trie blocks per touched account than the generated store and we called it a migrated trie costing more to update. The tries are the same shape. The snapshot's top-of-trie column had been rewritten in 4 KB blocks by the same read-write open that repaired the first item in this list, which transcribed the client's options for the column it meant to rewrite and left the rest on RocksDB's defaults; the audit after it checked two columns and missed the third. Swapping the two layouts moved the transfer cell from 1.074 to 1.014 and swapped the read counts with it. A read-write open of a store by tooling has to transcribe every column's options, not just the one being rewritten: an idle column with a compaction pending is rewritten under whatever the open carries.
  • We called an outlier reproducible because it appeared in two runs that shared a denominator. The regenerated store was measured twice, both times against the same jochemnet run, and a handful of tests sat 20–38% apart in both. Re-measuring 20 of them as a fresh pair moved jochemnet by up to 29% on a single test and took the largest transfer excursions back inside the band. Two runs of one arm are one measurement of the ratio, not two.
