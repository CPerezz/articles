How can two Nethermind databases holding the same state differ 17× — and then agree?

Ethereum · nethermind · flat DB · benchmarking · 2026 · reproducible pipeline & data →

1,461 tests matched by exact identity across both stores, zero gas mismatches. Nethermind nethermind:glamsterdam-devnet-7, --FlatDb.Enabled=true, rollback_strategy: container-recreate, drop_memory_caches: steps.

The behaviour

Two Nethermind databases. One is a mainnet shadowfork snapshot taken at block 24,402,727; the other is state generated from scratch by state-actor. The same EEST bloatnet fixtures run against both, on the same machine, with the page cache dropped between every test. Where the tests read accounts, the generated store reports up to 17× less throughput — and that headline is not a small-test artifact: the two categories carrying it run for a median of 10.2 and 9.4 seconds, with not one test under a second between them.

How to read a number on this page

Before any of it means anything: this suite contains two populations, and only one of them can carry a claim about a database. Run the same store twice under the same configuration and ask how often a test lands within ±10% of itself. Over five seconds, 97% of tests do. Under a fifth of a second, 39% do. A short test on this harness does not reproduce against itself, so a ±10% difference between two stores on a short test is not evidence of anything.

What we found wrong with the measurement

Four things, in the order they matter. Three are properties of how the arms were prepared — two in the store, one in the fixtures — and the fourth is the harness not having the controls this kind of study needs. All four were found by changing them and re-measuring, and only the first one moved the headline: the other three are here because each was a plausible cause that had to be killed by intervention rather than by argument.

  1. The pre-run is promoted into the baseline. Only one arm replays a pre-run before measuring, and the harness is told to promote the result into the image every test restores from. That leaves the benchmark's own accounts as the newest versions in the youngest files of the LSM tree. Diagnosed below, fixed, and the fix accounts for almost all of the gap.
  2. The client is restarted for every test, and the two arms warm up differently. A .NET process seconds old is still compiling itself. jochemnet's setup step is heavy EVM work, so its interpreter is promoted to optimised code before the measurement; state-actor's fixtures spend that window on an empty block, so its measured block runs on the unoptimised tier. Diagnosed below, fixed by intervention: equalising it moves the control tests from 0.73 to 1.14 and closes every remaining category.
  3. The generated store makes every client that opens it rewrite the store. Its trie column families were left in a state that RocksDB garbage-collects on open, so a client sitting completely idle read 1,962 MB from it in 60 seconds against jochemnet's 0 — and the harness restarts the client for every one of 1,463 tests, so the job never finished and never stopped. Diagnosed below, fixed in the generator, and it changed the throughput by almost nothing.
  4. The harness has no compaction control and no warm-up control. BENCHMARKOOR_COMPACT_BETWEEN_STEPS is named in a source comment, never implemented, and BENCHMARKOOR_POST_PRERUN_CMD is implemented on branch state-db-journal-drain only; absent from the binary these runs used. There is also no way to ask for a discarded burn-in block before the measured one. Both treatments below had to be applied by hand.

The root cause: the benchmark's keys live in a corner of one store

Only one arm runs a pre-run. Before measuring, the jochemnet arm replays 10.06 GB of blocks — 7,736 of them, 64 transactions each, taking the chain from 24,402,728 to 24,410,463 — which create the accounts the benchmark then reads. The harness is then told promote_post_pre_runs: true, which freezes that post-pre-run layout into the golden image every test is restored from.

This is not a caching story. The harness drops the page cache between every test, and the pre-run happens once, before the loop. What survives the drop is not warm memory — it is which files hold the current copy of each key.

The structure that matters here is not the Merkle trie but the LSM tree underneath it: Nethermind keeps the flat state in RocksDB, whose account column family is keyed by keccak256(address)[0:20]. Those keys are hashes, so they are scattered uniformly — nothing about the benchmark's accounts is adjacent in key order. What is concentrated is the set of files holding their newest versions. The pre-run rewrote every one of those accounts, so their current copies landed together in a handful of recently flushed SSTs near the top of the tree, and a levelled store answers a point lookup from the newest level that has the key and stops. The working set is therefore bounded by the size of those few files, not by the number of keys.

Stated that way the mechanism makes a prediction: merging those files down into the bottom level should destroy the advantage entirely, because afterwards no level holds a privileged copy. That is a compaction, it is testable, and the rest of this page is the test.

The per-lookup cost is not what differs — the number of distinct physical blocks is. Both stores pay about two blocks for a lookup they have not made before. One of them runs out of new blocks to read.

Finding 1: the pre-run is promoted into the baseline — and what compacting it does

The change, concretely. The treatment is a full RocksDB compaction of the affected column families: CompactRange over the whole key range with bottommost_level_compaction=kForce, which is required because a family that already sits entirely in its bottom level is a no-op for an ordinary compaction. The rewrite uses the other store's exact per-family options — filter policy, block size, restart interval, compression — verified knob by knob afterwards, so the only thing that changes is which file holds each key's newest copy. No value is touched and the state root is unchanged.

The pre-run is then removed from the arm's config. That is not a reduction of the workload: its writes are already in the promoted image, so the arm still starts from exactly the state the pre-run produced. Replaying it would simply write those accounts again and rebuild the very thing we just flattened.

The reproducible way to do this is the harness's post-pre-run hook (BENCHMARKOOR_POST_PRERUN_CMD), which runs an operator command after the pre-run and before the snapshot is promoted, aborting the promote if it fails. That hook lives on a branch and is not in the binary these runs used, so the compaction here was applied to the promoted image by hand. Same end state; the hook is the path anyone reproducing this should take.

Finding 2: the client is restarted for every test, and the two arms warm up differently

Every test runs against a freshly started client: container-recreate restores the image and boots Nethermind again, 1,463 times. That is the right way to keep tests independent. It also means every measured step runs inside a process that is seconds old, and a .NET process that is seconds old is still compiling itself: hot methods start in the unoptimised tier and are promoted in the background after a call-count threshold and a settling delay. Whether the EVM's inner loop has been promoted by the time the measured block arrives depends on what the process did in the seconds before — and the two arms' fixtures make it do different things.

What this is and is not. DOTNET_TieredCompilation=0 is the diagnostic, not the recommended configuration — a live node runs promoted, profile-guided code, and fully-optimised-on-first-call is slower to start and skips the profile guidance. What the benchmark needs is what a live node has: an EVM that has already crossed the tiering threshold before the block being measured. Concretely, the harness should give every arm the same EVM-heavy warm-up after boot — a burn-in block whose result is discarded — before the measured step. That is the pre-run problem again, one level down: not which files hold the keys, but which tier holds the code. Any JIT-hosted client restarted per test is exposed; ahead-of-time compiled clients are not, which is one reason the geth study found this cell open and could not close it from geth's side.

Finding 3: the generated store makes the client rewrite it

This one was found by asking a simpler question than the study had been asking: what does the client read when nobody is asking it for anything? Boot each arm, drop the page cache, issue zero queries, and watch the client's own /proc/<pid>/io for 60 seconds. jochemnet reads 0 MB. The generated store's client reads 1,962 MB, at roughly 33 MB/s, indefinitely, with every one of its threads at 0% CPU.

What it is. Per-thread attribution puts the traffic on rocksdb:low — 1,949 MB in 45 seconds — so it is RocksDB's own background compaction inside the client, not client code. The event log names the reason: 14 jobs at boot, all on StateNodes, all BottommostFiles. jochemnet's client starts 1 job, on StorageNodes, for the ordinary reason (LevelMaxLevelSize).

kBottommostFiles is RocksDB rewriting bottom-level files purely to zero out their sequence numbers: it marks every bottommost file whose largest_seqno != 0 once no snapshot protects it. So the trigger is not how much data is there or how the levels are shaped — it is how the files got there. The generator does finish by compacting, but with the default bottommost_level_compaction = kIfHaveCompactionFilter, and no compaction filter is configured anywhere. RocksDB therefore trivially moved the flushed L0 files into the empty bottom level rather than rewriting them. A moved file is not a rewritten file: the tree comes out flat, which is what the call was there to achieve, and every file keeps a non-zero sequence number.

That is why this survived thirty rounds of looking at level shape and pending-compaction bytes: in this condition both look perfectly healthy. It also means an idling node shows it only if the client takes and releases a snapshot at startup, which Nethermind does and Besu does not — on Besu the same store sits quiet until something asks it for state.

The fix, and what it costs. Run the finishing compaction with bottommost_level_compaction=kForce so the files are rewritten once, by the generator, instead of repeatedly by every consumer. Applied here to the trie families — 603→207 files on StateNodes in 422 s and 1,211→1,126 on StorageNodes in 2114 s, 331 GB and 42 minutes in total — it takes the idle client from 1,962 MB to 0 MB and the boot from 14 compaction jobs to 0. It is upstream as state-actor#139, which fixes the same call in the Besu, ethrex and reth writers too.

On a per-test byte column that is a couple of per cent; on the difference between two windows, which is the quantity that says what a distinct contract costs, it was most of the answer. With the store quiet, the attribution is finally about the test.

Class 2 in detail: which state access actually diverges

Everything from here to the end of this section is the 785 tests that run for more than a second. As a whole they now sit at 0.978 with 83% inside ±10%, so what is left is not a general slowness — it is specific, and two questions locate it. Does the opcode fetch the callee's code, or does it only read the account row? And is the contract a different one on every access, or the same one reused?

That is a single square of a 2×2, and it is the whole of what is left: it is not the account row, because the account-row opcodes are at parity under the same mode; and it is not distinctness on its own, because the same opcodes reusing one contract are at parity too. Only loading a distinct contract's code is expensive.

Finding 4: what is left is the code database, on distinct contracts

The fourth explanation was not in the store at all. Three store-level stories fit this square and each was contradicted by a direct measurement; a fourth was found by equalising the warm-up, which took the cell from 0.642 to 0.944. The direction is the instructive part: state-actor barely moved (15.1 to 14.5 s), while jochemnet slowed from 9.7 to 13.6 s. Its advantage here was reaching promoted code partway through a fifteen-second test that state-actor spent on the unoptimised tier — the same mechanism as the control loop, on a long test rather than a short one.

Two smaller store defects turned up while chasing this and are worth recording even though neither moved a ratio. The generated store's account column family was left L3:92 (23.7 GB), compaction-pending, so a freshly booted client restarted the same compaction on every test and the per-test rollback discarded it; rebuilding it to L6:92, pending 0 removed that background thread and changed the throughput by nothing measurable. The code database on both arms was in the same state — L4:734 (45.7 GB), compaction-pending on the generated store, L0:3 L1:6 L3:117 (6.9 GB), compaction-pending on the snapshot. The cause is a RocksDB detail worth knowing: a manual CompactRange writes its output into the deepest level that already holds files unless it is told change_level and a target, so a generator that finishes with a plain compaction leaves the store permanently compaction-pending. Both are the same family of mistake as Finding 3, caught earlier and on smaller column families.

With the phantom gone the two probes say something clean, and for the first time they agree with the throughput. On access patterns that touch no code — BALANCE against EOAs, EXTCODESIZE against minimal contracts — the two stores are byte-for-byte alike: state-actor's marginal is 19.3 MB from flat/Account against jochemnet's 16.2 MB across its whole datadir, and the trie families contribute nothing (0.0 MB, down from 689). Those are exactly the cells sitting at 0.997 and 0.995 in the table above.

On the pattern that touches a distinct maximum-size contract per access, measured over 6 matched pairs per arm (three code-loading opcodes at two gas points), the generated store pays 2,821 MB against the snapshot's 1,671 MB — 1.69× the bytes for the same work, of which 2,444 MB is the code database itself. Its account rows are identical between the two patterns (-1.0 MB), and its trie families still contribute nothing (-0.1 MB). So the residual is one thing: fetching bytecode the store has never fetched before.

That is consistent with the throughput and with the shape of the two code databases. The snapshot dedups bytecode by code hash; the generated store keys it per account, so it holds 45 GB against 7.6 GB and its entries are far smaller and far more numerous. Nothing about that is a bug — it is what generating distinct contracts means — but it does mean a benchmark that touches a new contract on every access reads more from it. What remains unexplained is now only the size of the effect: 1.69× the bytes coming out as 7% less throughput, with the client using 0.79 of the snapshot's CPU for the same work. The fixture accounts are not the answer: all 20,000 addresses in the range the tests use carry no code at all on either arm.

Class 1: why the sub-second tests are not evidence

The other 676 tests — 46% of the suite — sit at a median of 0.767 and reproduce 18% of the time against a floor of 49%. They are not a quieter version of the same signal; they are the harness measuring itself. Every category that is still far from parity after treatment lives entirely here:

What is actually being measured here is the process, not the database. A client restarted for every test spends its first moments compiling itself, which is Finding 2's mechanism and why equalising warm-up moves this class from 0.73 to 1.14 — past parity, because the intervention then costs jochemnet the promoted code it used to reach mid-test. A treatment that overshoots is a treatment aimed at the wrong quantity; the honest reading is that neither configuration measures a store here.

It is also not the client's cache, which is the explanation we pre-registered and lost: starving the flat database's block cache 1024 MiB → 8 MiB moved this class by 3%, and removing every page-cache drop took state-actor's control reads to zero without making it faster.

None of this means the sub-second tests are worthless — they are the reason the warm-up asymmetry was found at all, because an effect that is a rounding error on a ten-second test is most of a tenth-of-a-second one. It means they cannot be quoted as a ratio between two databases, which is what earlier versions of this page did.

What to do about it

  1. Never compare a promoted-after-pre-run snapshot against a store that did not get one. It is worth an order of magnitude and it does not announce itself.
  2. Neutralise the pre-run's placement effect on the arm that has one — compact after the pre-run, before the snapshot is promoted. That is a single compaction per baseline, and the harness already has the right hook for it (BENCHMARKOOR_POST_PRERUN_CMD), though it is implemented on branch state-db-journal-drain only; absent from the binary these runs used. Note what not to do: compacting between every test's steps, the lever geth could reach over RPC, costs 185 s per column family here — about 3.1 days across 1,463 tests, six times the runtime of the suite it would be preparing.
  3. Give every arm the same EVM warm-up before the measured block. This is the one that cost us the most rounds. A client restarted per test measures a process that is still compiling itself, and whichever arm's fixtures happen to do heavy EVM work in the seconds before the measurement gets promoted code for free. Here the two arms differ by a single empty block, and it is worth 57% on the control tests. The fix is a burn-in block whose result is discarded, identical on every arm — not disabling tiered compilation, which is the diagnostic and biases the other way.
  4. Finish a generated store's compaction with kForce and an explicit target level — the two halves of the same mistake, and the only one of these items that is a bug in the artifact rather than in the methodology. Without a target level a plain CompactRange writes into the deepest level that already holds files, leaving the store permanently compaction-pending. Without bottommost_level_compaction=kForce it does something quieter and worse: with no compaction filter configured it moves the flushed files into the bottom level instead of rewriting them, so every file keeps a non-zero sequence number and the first client to open the store starts garbage-collecting all of them. That was worth 1,962 MB of background I/O per 60 idle seconds here, restarted on every one of 1,463 tests. Both are one-line changes at generation time, 42 minutes for 331 GB, paid once by the producer instead of repeatedly by every consumer (state-actor#139). Worth doing for reproducibility even though it moved no ratio here.
  5. Give the harness control of the client's cache, not just the page cache — but do not expect it to explain much. Starving the block cache here moved the result by 3%, and removing the page-cache drops entirely took state-actor's control reads to zero without making it faster. Useful control, wrong suspect.
  6. Print a locality diagnostic: read bytes per unit of gas, per arm. Flat in gas means a bounded working set and therefore an artifact — jochemnet read 227 MB at 100M and 232 MB at 300M while state-actor climbed from 1986 to 5772 MB. That check is a few lines, and it would have caught this on the first run rather than the thirtieth.
  7. Report per duration class, and never aggregate across the boundary. This is the cheapest of these and it would have saved the most rounds. Measure the floor first — one store, twice — then report tests that clear it separately from tests that do not. Here 46% of the suite runs in under a second and reproduces 18% of the time, so a category median computed over both classes is an average of a measurement and an artifact. The storage tests are the demonstration: the same category on the same pair of stores reads 1.468 below a second and 1.007 above it.

And the answer to the question in the title: the generated state was never 17× slower. With placement equalised, account reads agree within 2–3%, storage within 3%, ether transfers within 1%, and absent-account lookups resolve from a filter in 2.5 against 2.8 microseconds. Synthetic state is a sound substitute for benchmarking state access.

One caveat stops that being a blanket endorsement, and it is narrower than it was. Executing a distinct maximum-size contract still costs the generated store 1.06× once both arms measure steady-state code — down from 1.56× as published — and with the store no longer compacting itself underneath the measurement, that remainder has a clean account: 1.69× the bytes for the same work, essentially all of it the code database, while the client uses 0.79 of the snapshot's CPU. So code-execution-heavy workloads are mostly covered now, with a residual worth roughly 6% on the one access pattern that touches a new contract every time — and that residual is a property of generating distinct contracts, not a defect anyone can patch away.

And the reason that sentence can be said plainly now, where earlier versions of this page hedged: the 676 tests that could not support it are reported separately instead of averaged in. The control category alone — 440 tests at 0.12 s doing no account work — carried more of the published divergence than any category that reads state, and it never belonged in a comparison between two databases.

What we got wrong on the way

  • The first compaction used RocksDB's default table options, which silently dropped the ribbon filter and switched to Snappy. Absent-account lookups inverted to a 19× advantage for the generated store, and it took a full re-run with the real per-family options to get the parity figure above.
  • A rebuild was applied to the mounted volume without promoting it, so the harness restored the untreated image before the first test and a 2.2-hour run measured nothing new. It became an accidental replication, which is the only reason we can quote a run-to-run noise figure.
  • The probe measured both stores as if they had no filters. It opened every column family with RocksDB's default options, and a reader with no filter_policy configured never consults the filters that are in the files. Absent and present lookups therefore cost the same, which made us retract a correct explanation. Opened properly, the filters work on both arms — 19,821 and 19,786 of 20,000 negatives rejected — and an absent lookup costs 73 against 7,314 bytes.
  • We published a mechanism for the last cell and it was wrong. The residual was attributed to the generated store's larger code database. Three direct measurements say the opposite: reading code is cheaper on that store per lookup, cheaper on a sweep of distinct maximum-size contracts, and the two stores hold the same number of them. The section above now reports the cell as open.
  • We had a fourth explanation and it failed too. The control gap looked like cross-step cache carry-over, and we pre-registered the prediction that starving the block cache would pull it to 0.85–0.95. It moved to 0.707. The section above reports the eliminated explanation rather than the one we expected to be writing, which is the only reason this list is worth keeping.
  • We reported per-test divergence counts before measuring whether a test reproduces. Running the same store twice under the same configuration puts only 75% of 133 tests inside ±10% of themselves — 39% for tests under a fifth of a second against 97% for tests over five seconds. An earlier version of this page ranked the twelve most divergent tests in the suite; all twelve ran in under 0.2 s, so that table was a ranking of the noisiest measurements. It is gone, and the dispersion figure now states the floor.
  • We blamed the wrong subsystem three times for the same gap. First the client's block cache, refuted by starving it. Then a background compaction the generated store really was running, refuted by settling the account family and watching the throughput not move. Then a much larger one on the trie families — 1,962 MB per 60 idle seconds, Finding 3 above — where the prediction on record was that most of the remaining gap would close, and it moved +0.007. The one that did explain the bulk of it was the JIT, visible only by looking at the client's threads rather than its I/O. Three of the four were eliminated by intervention rather than argument, which is the only reason the fourth was reachable.
  • We attributed bytes to the test while the store was reading on its own account. The generated store's client was compacting in the background throughout every run, and the per-column-family probes compare two separate runs — one filtered to DIFF_MAX, one to SAME_MAX, each with its own boot — so that traffic enters each window in proportion to how long the window stayed open rather than to what the test did. It landed on the difference between two large numbers, which is exactly the quantity we were reading. The effect on the per-test byte columns elsewhere in this page is small by comparison: at the measured idle rate of 33 MB/s and a DIFF_MAX test length of 1.8 s, about 58 MB against read volumes in the thousands. Re-measured on the settled store, the marginal cost of a distinct contract is 1.69× rather than the 3.15× the same probe reported while the compaction was running, and the 689 MB of trie reads we had attributed to non-code account lookups turned out to be 0. An I/O measurement taken while the store is doing its own I/O measures the store, not the test.
