How can two Nethermind databases holding the same state differ 17×?

Ethereum · nethermind · flat DB · benchmarking · 2026 · reproducible pipeline & data →

A mainnet snapshot, a generated store, the same benchmark suite. Five reasons the numbers disagreed, and what is left once all five are fixed.

The problem

We ran the same EEST bloatnet suite against two Nethermind databases holding the same logical state: jochemnet, a mainnet shadowfork snapshot at block 24,402,727, and a store generated from scratch by state-actor. Same fixtures, same machine, page cache dropped between tests. If the two stores were equivalent, every test would run at the same speed on both. They didn't: where the tests read accounts, the generated store looked up to 17× slower.

Each test is two blocks. A setup block deploys or funds what the test needs; then the measured block does the work, thousands of cold account lookups, contract calls, storage writes or transfers sized to a gas budget (160M and 240M here). Before every test the harness restores the store from a golden image and boots a fresh client, and it drops the page cache between the two blocks, so each measured block starts cold. Both arms run the same Nethermind image with the same flags, reading through its flat state database.

The gap came apart into five findings, each fixed and measured on its own:

  1. The snapshot's pre-run was baked into its baseline.
  2. The client restarts for every test, and the two stores warm it up differently.
  3. The generated store made the client rewrite it on every boot.
  4. What shares a code block with the contract being read.
  5. Two storage columns nobody had compacted.

How to read the numbers. Every ratio is state-actor's throughput over jochemnet's on the same test: 1.00 is parity, below 1 the generated store is slower. We split the suite at one second of measured time, because a sub-second test doesn't reproduce against itself. Measure the same store twice and 96–100% of the longer tests land within ±10% of their first result, but only 41–61% of the short ones. Short tests appear in every view below, but we read no store difference from them.

Finding 1: the snapshot's pre-run was baked into its baseline

Before measuring, the jochemnet arm replays 7,736 blocks that create the accounts the benchmark reads, and the harness promotes the result into the image every test restores from. Those accounts are then the newest versions in the youngest files of the LSM tree: a handful of recently flushed files near the top, where a cold lookup finds them in one or two reads. On the generated store the same accounts are spread through a fully compacted tree, which is what a cold read on a real node looks like. The baseline compared a hot corner of one store with the whole of the other.

Two measurements say it is placement and not content. On keys sampled from each store's own contents instead of the benchmark's, jochemnet is the more expensive store: 10.26 blocks per trie-node lookup against 3.44. Its data isn't cheaper to read; the benchmark's keys are. And as the benchmark reads more accounts, jochemnet's read volume stops growing: 47 MB for 50,000 lookups, 0.23 blocks each, because the same few files serve all of them. state-actor reads 404 MB at 1.97 blocks each, flat. A working set that stops growing is the signature of a hot corner.

We fixed it the way a real node would have: compact the snapshot, so its benchmark accounts sit where every other key does. Nothing about the generated store changed.

Across the full sweep, 1,461 tests at 11 gas levels from 100M to 300M, the share that agree within ±10% went from 12.8% to 53.0%, and the long class's median from 0.18 to 0.98. That is the bulk of the 17×. What it left behind is distinct-contract code at 0.87, and a sub-second class that got no better, which is the next finding.

Finding 2: the client restarts for every test, and the stores warm it up differently

The harness restarts Nethermind for every test, so tests stay independent. That means every measured block runs in a .NET process a few seconds old, which is still compiling itself: hot methods start in an unoptimised tier and get promoted in the background. jochemnet's setup step is heavy EVM work, so its interpreter is promoted by the time the measured block arrives. state-actor's setup is an empty block, so its measured block runs unoptimised. The tiering thread alone takes 70% of jochemnet's measured-step CPU and 34–50% of state-actor's.

The control tests show it most cleanly, because they do no state work at all: they measure the process. Their setup block reads 31 MB on jochemnet and 9 MB on state-actor, and their measured block ran at 0.73, the generated store slower on a test that never touches the store.

The other suspect for a process-level gap was parallel execution, and it points the wrong way: turning it off moved the controls to 0.56, further from parity, not closer.

The fix is a harness setting, not a store change, and it equalises the arms rather than making them realistic: a live node's EVM is long past the tiering threshold. It also makes the sub-second account tests at least 2.0× faster on both arms, which says how much of a short test is the process warming up. The honest fix is a discarded burn-in block before every measured one; the harness can't do that yet, so every number from here on is taken with tiered compilation off on both sides.

Finding 3: the generated store made the client rewrite it on every boot

state-actor finished its store with a plain CompactRange. With no compaction filter configured, RocksDB moves the flushed files into the bottom level instead of rewriting them, so their sequence numbers stay set. Every client that opens the store starts rewriting its bottom files, and since the harness restarts the client per test, that rewrite restarted 1,463 times and never finished. An idle client with zero queries read 1,962 MB in 60 seconds.

The client's own event log names it: 14 compaction jobs at every boot, reason BottommostFiles, on a store with nothing pending.

Forcing the bottommost rewrite silenced it: idle reads went from 1,962 MB to 0. The fix is now in the generator as state-actor#139. Throughput moved by +0.007. A real defect, and not the cause.

Finding 4: what shares a code block with the contract being read

With the first three fixed, one thing still separated the stores on long tests: executing a contract the store had never served. Distinct-contract code sat at 0.938 and jump-destination scanning at 0.943, while the same opcodes on one reused contract were at 1.000.

Code is keyed by its hash, so a contract's neighbours in a data block are random. What differs is who they are. RocksDB packs records into a block until it passes the target size, so a 24 KB fixture contract usually lands after a tail of whatever was written before it, and fetching the contract reads that tail too. On the snapshot the tail is real mainnet contracts, median 45 bytes, which compress. On the generated store it was the filler pool's 23-byte stubs, which don't.

Besu shows the same shape on its own generated store: distinct-contract code at 0.83 against 0.94 for the reused contract. Two clients, one generator artifact.

To prove it we rewrote the generated code database with a 64-byte block, so every contract sits alone: same keys, same values, same state root. The two cells went to 1.008 and 1.015; the reused-contract control stayed at 0.996.

The 64-byte block is a diagnostic, not a fix. The fix belongs in the generator: state-actor#141 slices the pool from real mainnet bytecode at mainnet compressibility. On a store regenerated with it the two cells read 1.05–1.10: fixed, and a little past parity, for a reason we come back to at the end.

Finding 5: two storage columns nobody had compacted

The snapshot's storage rows sat in 807 files spread over 6 levels, its storage trie in 1,961 over 5; the generated store keeps each in one level. A lookup for a key that isn't there has to be refused by every level that could hold it, so on one test the snapshot issued 3,770 storage reads where the generated store issued 900. Finding 1 compacted the columns the account tests read; storage was at parity from the first run, so nobody looked at it.

The pre-run is why. Its 7,736 blocks of 64 transactions each write storage, and every flush lands fresh files at the top of the tree that cascade down over the following compactions. The account column had been settled by hand; the storage ones hadn't.

Each step was registered on its reads before it ran, and both read predictions held: storage-row reads on the absent-slot test fell to 850 against the generated store's 952, and storage-trie reads to 61,457 against 61,739.

Where it stands

With all five fixed, we ran the whole suite on both stores twice, as two pairs that share no run: the snapshot's pre-run and storage columns compacted, the generator on the fixed pool with #139's compaction, tiered JIT off on both arms. Each store is also measured against itself, so the floor sits beside the comparison.

Read left to right, the long class moves in four steps. Compacting the pre-run takes it from 0.18 to 0.98. Equalising the JIT and settling the store adds a little, mostly on distinct-contract code (0.87 → 0.94). The regenerated pool moves that one family past parity (1.09) and nothing else. Settling the storage columns closes storage and leaves the rest where it was. The short class moves only when the JIT is equalised, and then stops at its floor.

17 of the 144 long tests still miss the band in both pairs, and they are not spread across the suite: 12 are distinct-contract code, where the regenerated pool overshoots, and 5 are transfers, led by the transfer to an absent account at 1.53. The other 43 misses are sub-second.

As a family, transfers reach 1.054, with 29 of 36 in the band. The ones that miss issue the same reads on both stores. The worst reads 918 accounts on state-actor and 920 on jochemnet, and 3,358 against 3,385 top-of-trie nodes; every transfer outlier we traced is within 5% on every column. What is left there is not I/O.

What is left, and why

The code pool overshoots. #141 draws its records from mainnet bytecode, but keeps a 1 KiB floor on record size. Mainnet's median contract is 45 bytes, so on Nethermind's 4 KB code block a fixture contract now starts a block of its own more often than it would on mainnet, and reading it is cheaper. Same mechanism as Finding 4, sign reversed. The pool was tuned against a 32 KB block, which is what Besu uses and where a 24 KB fixture contract shares its block with other records either way; Nethermind's 4 KB block is where the floor shows. The fix is to draw record sizes from mainnet's distribution rather than a floor, in the generator.

Absent-key work costs the snapshot more CPU. Transfers to accounts that don't exist issue the same reads on both stores, for the same bytes at the same latency, yet jochemnet spends 2.14 CPU-seconds in managed worker threads where state-actor spends 1.23. Turning off state pre-warming or the trie warmer doesn't change it. It is client work, and the next instrument is a profiler, not another benchmark.

Sub-second tests can't be read at any store shape. Measured against itself, state-actor puts 41% of them within ±10% and jochemnet 61%. A per-test restart plus a JIT still warming up is most of what a short test measures. That is fixed in the harness, with a discarded burn-in block, not in either store.

The lesson is the one the geth study reached from the other side. A snapshot that was replayed into shape carries its history: whatever was written last is in the youngest files, and whatever was never compacted stays a stack of levels. A generated store has none of that; it is uniform by construction. Equalising the two makes them comparable. It does not make the generated one look like mainnet, and a benchmark that wants to know how an aged, fragmented store behaves needs one.

Earlier versions of this page attributed the transfer tests' small edge first to a migrated trie costing more to update, then to per-read cost on a mainnet-shaped trie. The traces refute both: those tests issue identical reads on both stores. The numbers in this page are computed from the collected run data at build time, and the generator refuses to emit the page if the data stops supporting a sentence above.
