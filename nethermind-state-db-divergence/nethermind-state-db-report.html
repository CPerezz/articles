How can two Nethermind databases holding the same state differ 17× — and then agree?

Ethereum · nethermind · flat DB · benchmarking · 2026 · reproducible pipeline & data →

1,461 tests matched by exact identity across both stores, zero gas mismatches. Nethermind nethermind:glamsterdam-devnet-7, --FlatDb.Enabled=true, rollback_strategy: container-recreate, drop_memory_caches: steps.

The behaviour

Two Nethermind databases. One is a mainnet shadowfork snapshot taken at block 24,402,727; the other is state generated from scratch by state-actor. The same EEST bloatnet fixtures run against both, on the same machine, with the page cache dropped between every test. Where the tests read accounts, the generated store reports up to 17× less throughput.

What we found wrong with the measurement

Three things, in the order they matter. Two are properties of how the arms were prepared — one in the store, one in the fixtures — and the third is the harness not having the controls this kind of study needs. All three were found by changing them and re-measuring.

  1. The pre-run is promoted into the baseline. Only one arm replays a pre-run before measuring, and the harness is told to promote the result into the image every test restores from. That leaves the benchmark's own accounts as the newest versions in the youngest files of the LSM tree. Diagnosed below, fixed, and the fix accounts for almost all of the gap.
  2. The client is restarted for every test, and the two arms warm up differently. A .NET process seconds old is still compiling itself. jochemnet's setup step is heavy EVM work, so its interpreter is promoted to optimised code before the measurement; state-actor's fixtures spend that window on an empty block, so its measured block runs on the unoptimised tier. Diagnosed below, fixed by intervention: equalising it moves the control tests from 0.73 to 1.14 and closes every remaining category.
  3. The harness has no compaction control and no warm-up control. BENCHMARKOOR_COMPACT_BETWEEN_STEPS is named in a source comment, never implemented, and BENCHMARKOOR_POST_PRERUN_CMD is implemented on branch state-db-journal-drain only; absent from the binary these runs used. There is also no way to ask for a discarded burn-in block before the measured one. Both treatments below had to be applied by hand.

The root cause: the benchmark's keys live in a corner of one store

Only one arm runs a pre-run. Before measuring, the jochemnet arm replays 10.06 GB of blocks — 7,736 of them, 64 transactions each, taking the chain from 24,402,728 to 24,410,463 — which create the accounts the benchmark then reads. The harness is then told promote_post_pre_runs: true, which freezes that post-pre-run layout into the golden image every test is restored from.

This is not a caching story. The harness drops the page cache between every test, and the pre-run happens once, before the loop. What survives the drop is not warm memory — it is which files hold the current copy of each key.

The structure that matters here is not the Merkle trie but the LSM tree underneath it: Nethermind keeps the flat state in RocksDB, whose account column family is keyed by keccak256(address)[0:20]. Those keys are hashes, so they are scattered uniformly — nothing about the benchmark's accounts is adjacent in key order. What is concentrated is the set of files holding their newest versions. The pre-run rewrote every one of those accounts, so their current copies landed together in a handful of recently flushed SSTs near the top of the tree, and a levelled store answers a point lookup from the newest level that has the key and stops. The working set is therefore bounded by the size of those few files, not by the number of keys.

Stated that way the mechanism makes a prediction: merging those files down into the bottom level should destroy the advantage entirely, because afterwards no level holds a privileged copy. That is a compaction, it is testable, and the rest of this page is the test.

The per-lookup cost is not what differs — the number of distinct physical blocks is. Both stores pay about two blocks for a lookup they have not made before. One of them runs out of new blocks to read.

Defect 1: the pre-run is promoted into the baseline — and what compacting it does

The change, concretely. The treatment is a full RocksDB compaction of the affected column families: CompactRange over the whole key range with bottommost_level_compaction=kForce, which is required because a family that already sits entirely in its bottom level is a no-op for an ordinary compaction. The rewrite uses the other store's exact per-family options — filter policy, block size, restart interval, compression — verified knob by knob afterwards, so the only thing that changes is which file holds each key's newest copy. No value is touched and the state root is unchanged.

The pre-run is then removed from the arm's config. That is not a reduction of the workload: its writes are already in the promoted image, so the arm still starts from exactly the state the pre-run produced. Replaying it would simply write those accounts again and rebuild the very thing we just flattened.

The reproducible way to do this is the harness's post-pre-run hook (BENCHMARKOOR_POST_PRERUN_CMD), which runs an operator command after the pre-run and before the snapshot is promoted, aborting the promote if it fails. That hook lives on a branch and is not in the binary these runs used, so the compaction here was applied to the promoted image by hand. Same end state; the hook is the path anyone reproducing this should take.

Defect 2: the client is restarted for every test, and the two arms warm up differently

Every test runs against a freshly started client: container-recreate restores the image and boots Nethermind again, 1,463 times. That is the right way to keep tests independent. It also means every measured step runs inside a process that is seconds old, and a .NET process that is seconds old is still compiling itself: hot methods start in the unoptimised tier and are promoted in the background after a call-count threshold and a settling delay. Whether the EVM's inner loop has been promoted by the time the measured block arrives depends on what the process did in the seconds before — and the two arms' fixtures make it do different things.

The test: take the JIT out of the measurement

Two levers, each on both arms, same 40 control tests. Not because state-actor got faster: jochemnet got slower, from 9.7 to 13.6 s per test, once it could no longer reach promoted code partway through a 15-second test that state-actor spent on the unoptimised tier. Three store-level explanations for this cell were each refuted by direct measurement; the fourth was never in the store. The short tests tell the same story from the other side: warm-query and same-key storage tests run 5–6× faster on both arms with tiering off, because as published they were measuring an interpreter that had not finished compiling.

What this is and is not. DOTNET_TieredCompilation=0 is the diagnostic, not the recommended configuration — a live node runs promoted, profile-guided code, and fully-optimised-on-first-call is slower to start and skips the profile guidance. What the benchmark needs is what a live node has: an EVM that has already crossed the tiering threshold before the block being measured. Concretely, the harness should give every arm the same EVM-heavy warm-up after boot — a burn-in block whose result is discarded — before the measured step. That is the pre-run problem again, one level down: not which files hold the keys, but which tier holds the code. Any JIT-hosted client restarted per test is exposed; ahead-of-time compiled clients are not, which is one reason the geth study found this cell open and could not close it from geth's side.

What we ruled out

The obvious answer is the code database: the generated store's is 45 GB against 7.6 GB. Measured three ways, it is wrong in every one of them.

What is still open

The fourth explanation was not in the store at all. Three store-level stories fit this square and each was contradicted by a direct measurement; a fourth was found by equalising the warm-up, which took the cell from 0.642 to 0.944. The direction is the instructive part: state-actor barely moved (15.1 to 14.5 s), while jochemnet slowed from 9.7 to 13.6 s. Its advantage here was reaching promoted code partway through a fifteen-second test that state-actor spent on the unoptimised tier — the same mechanism as the control loop, on a long test rather than a short one.

Two store defects turned up while chasing this and are worth recording even though neither moved a ratio. The generated store's account column family was left L3:92 (23.7 GB), compaction-pending, so a freshly booted client restarted the same compaction on every test and the per-test rollback discarded it; rebuilding it to L6:92, pending 0 removed that background thread and changed the throughput by nothing measurable. The code database on both arms was in the same state — L4:734 (45.7 GB), compaction-pending on the generated store, L0:3 L1:6 L3:117 (6.9 GB), compaction-pending on the snapshot. The cause is a RocksDB detail worth knowing: a manual CompactRange writes its output into the deepest level that already holds files unless it is told change_level and a target, so a generator that finishes with a plain compaction leaves the store permanently compaction-pending.

What remains genuinely unexplained is small and it is I/O, not compute: with warm-up equalised, executing a distinct maximum-size contract still costs the generated store 1.06×, on 4.9 GB of reads per test, while using only 0.79 of the snapshot's CPU for the same work — it is waiting, not computing. The fixture accounts are not the answer: all 20,000 addresses in the range the tests use carry no code at all on either arm.

That is what a methodology artifact looks like, as opposed to a property of any one database.

What to do about it

  1. Never compare a promoted-after-pre-run snapshot against a store that did not get one. It is worth an order of magnitude and it does not announce itself.
  2. Neutralise the pre-run's placement effect on the arm that has one — compact after the pre-run, before the snapshot is promoted. That is a single compaction per baseline, and the harness already has the right hook for it (BENCHMARKOOR_POST_PRERUN_CMD), though it is implemented on branch state-db-journal-drain only; absent from the binary these runs used. Note what not to do: compacting between every test's steps, the lever geth could reach over RPC, costs 185 s per column family here — about 3.1 days across 1,463 tests, six times the runtime of the suite it would be preparing.
  3. Give every arm the same EVM warm-up before the measured block. This is the one that cost us the most rounds. A client restarted per test measures a process that is still compiling itself, and whichever arm's fixtures happen to do heavy EVM work in the seconds before the measurement gets promoted code for free. Here the two arms differ by a single empty block, and it is worth 57% on the control tests. The fix is a burn-in block whose result is discarded, identical on every arm — not disabling tiered compilation, which is the diagnostic and biases the other way.
  4. Finish a generated store's compaction with an explicit target level. A plain CompactRange writes into the deepest level that already holds files, so a store built bottom-up stays compaction-pending and every client that opens it restarts the same background job. Both arms' code databases and the generated store's account family were in that state; change_level plus a target level fixes it. Worth doing for reproducibility even though it moved no ratio here.
  5. Give the harness control of the client's cache, not just the page cache — but do not expect it to explain much. Starving the block cache here moved the result by 3%, and removing the page-cache drops entirely took state-actor's control reads to zero without making it faster. Useful control, wrong suspect.
  6. Print a locality diagnostic: read bytes per unit of gas, per arm. Flat in gas means a bounded working set and therefore an artifact — jochemnet read 227 MB at 100M and 232 MB at 300M while state-actor climbed from 1986 to 5772 MB. That check is a few lines, and it would have caught this on the first run rather than the thirtieth.

And the answer to the question in the title: the generated state was never 17× slower. With placement equalised, account reads agree within 2–3%, storage within 3%, ether transfers within 1%, and absent-account lookups resolve from a filter in 2.5 against 2.8 microseconds. Synthetic state is a sound substitute for benchmarking state access.

One caveat stops that being a blanket endorsement, and it is narrower than it was. Executing a distinct maximum-size contract still costs the generated store 1.06× once both arms measure steady-state code — down from 1.56× as published — and that remainder is I/O: the same work uses 0.79 of the snapshot's CPU. So code-execution-heavy workloads are mostly covered now, with a residual worth roughly 6% on the one access pattern that touches a new contract every time.

The control tests — the ones doing no account work at all, which carried more of the published divergence than any real category — were measuring the harness, not either store. They are the reason to read the corrected column above as a bracket rather than a verdict: neither configuration is neutral, and the honest range for every state-reading category lies between them, within a few per cent of parity in both.

What we got wrong on the way

  • The first compaction used RocksDB's default table options, which silently dropped the ribbon filter and switched to Snappy. Absent-account lookups inverted to a 19× advantage for the generated store, and it took a full re-run with the real per-family options to get the parity figure above.
  • A rebuild was applied to the mounted volume without promoting it, so the harness restored the untreated image before the first test and a 2.2-hour run measured nothing new. It became an accidental replication, which is the only reason we can quote a run-to-run noise figure.
  • The probe measured both stores as if they had no filters. It opened every column family with RocksDB's default options, and a reader with no filter_policy configured never consults the filters that are in the files. Absent and present lookups therefore cost the same, which made us retract a correct explanation. Opened properly, the filters work on both arms — 19,821 and 19,786 of 20,000 negatives rejected — and an absent lookup costs 73 against 7,314 bytes.
  • We published a mechanism for the last cell and it was wrong. The residual was attributed to the generated store's larger code database. Three direct measurements say the opposite: reading code is cheaper on that store per lookup, cheaper on a sweep of distinct maximum-size contracts, and the two stores hold the same number of them. The section above now reports the cell as open.
  • We had a fourth explanation and it failed too. The control gap looked like cross-step cache carry-over, and we pre-registered the prediction that starving the block cache would pull it to 0.85–0.95. It moved to 0.707. The section above reports the eliminated explanation rather than the one we expected to be writing, which is the only reason this list is worth keeping.
  • We reported per-test divergence counts before measuring whether a test reproduces. Running the same store twice under the same configuration puts only 75% of 133 tests inside ±10% of themselves — 39% for tests under a fifth of a second against 97% for tests over five seconds. An earlier version of this page ranked the twelve most divergent tests in the suite; all twelve ran in under 0.2 s, so that table was a ranking of the noisiest measurements. It is gone, and the dispersion figure now states the floor.
  • We blamed the wrong subsystem twice for the same gap. First the client's block cache, refuted by starving it; then a background compaction the generated store really was running, refuted by settling the store and watching the throughput not move. The cause was the JIT, which is visible only if you look at the client's threads rather than its I/O. Two of the three were eliminated by intervention rather than argument, which is the only reason the third was reachable.
